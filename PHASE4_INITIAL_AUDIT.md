# ProxiSpeak Phase 4 — Initial Audit and Implementation Plan

**Date:** October 18, 2026
**Scope:** audit only. No application source was modified in this phase. The only
file created is this report. `dist/` was regenerated by the required build and is
byte-identical in name/size to the Phase 3.10 artifact.
**Baseline window:** 18:58–19:15 local time, Windows, Node v24.18.0, Docker 29.4.3.

---

## 1. Executive summary

The Phase 3.10 implementation is present, coherent, and mostly reproducible. All
server, browser, database, and synthetic-media suites pass at the audited baseline.
The security model (signed, expiring, room-bound session tokens; authenticated
handshake; room-scoped signaling; fail-closed production guards) is implemented and
exercised by real-process tests. The WebRTC path completes real peer connections,
carries RTP in both directions with synthetic media, renegotiates after microphone
cycles, recovers from a transport interruption, and attenuates independent peers by
distance.

Two things prevent a clean production go/no-go:

1. **The frontend jsdom suite is not currently green.** Three consecutive full runs
   each produced **151 passed / 2 failed**, with `Test timed out in 5000ms`. The
   failing tests differ between runs (interaction + persistence twice, then
   microphone + persistence), and the same suite was green in Phase 3.10. This is
   consistent with machine-load-sensitive timing in the tests, not with a specific
   product assertion, but it must be stabilized before the suite can serve as
   release evidence. Per instruction, it was **not fixed** during this audit.
2. **The flagship real-world requirements remain unverified by construction**:
   physical microphone-to-speaker audio, real TURN relay connectivity, and browser
   media beyond three synthetic peers. No evidence exists for 50 concurrent *media*
   users; only server signaling was measured.

The signaling baseline is healthy: 50 Socket.io clients in one room sustained
~4,737 fan-out messages/s with 100% acknowledged position updates and 10.8% of one
core in this run. That is **not** a media scalability result.

**Recommendation:** **NO-GO for production / public exposure.** A controlled,
trusted-network pilot with at most 4 participants is conditionally acceptable once
the P0 manual audio checklist and the P1 HTTPS/refresh items pass. Phase 4 should be
implemented in the order in §8.

## 2. Actual architecture and relevant file paths

### Runtime topology

- **Frontend:** React SPA (`src/`), served by Vite. `vite.config.js` proxies `/api`
  to `http://localhost:4000` for both `server` and `preview`, and bakes
  `VITE_SOCKET_URL` (default `http://localhost:4000`) into the bundle.
- **Backend:** Express + Socket.IO (`server/server.js`), optional MongoDB
  (`server/db.js`), P2P WebRTC mesh negotiated through Socket.IO (`server/webrtc.js`).
- **Media:** browser-to-browser `RTCPeerConnection`; no SFU. One audio transceiver per
  peer, gain node per peer.
- **Coordinates:** virtual floor percentages (0–100), converted to pixels for
  collision and earshot distance. Not geographic.

### Authentication and session lifecycle

| Concern | File / location |
|---|---|
| Token creation, HMAC signing, claims, expiry, verification | `server/auth.js` (`issueSession`, `verifySessionToken`, `createAuthConfig`) |
| HTTP issuance and ICE endpoint | `server/server.js:211` (`POST /api/auth/session`), `:253` (`GET /api/ice`) |
| Handshake validation before any handler | `server/server.js:282` (`io.use`) |
| Session/room binding, identity, single-socket eviction | `server/server.js:370-427`, `:400-405`, `:475-477` |
| Client issuance, in-memory token, ICE fetch | `src/utils/auth.js` (`requestSession:64`, `fetchIceServers:112`) |
| Handshake attachment and expired-token refresh | `src/utils/socket.js:43-51`, `:65-83` |
| Bootstrap before socket creation | `src/pages/VirtualOffice.jsx:143-166`, gate at `:179` |

Token format: `v1.<base64url(claims JSON)>.<base64url(HMAC-SHA256)>`; claims
`{v, sub, name, room, jti, iat, exp}`; default TTL 3600 s; subject is a server UUID.
Production requires `SESSION_SECRET` (>= 32 chars). Development uses a labelled
fallback. `JOIN_CODE` (optional, >= 12 chars) gates issuance in production when
`AUTH_ALLOW_ANONYMOUS` is false.

### Room membership and authorization

- `ALLOWED_ROOMS` (optional) at issuance and join: `server/config.js`
  (`sanitizeRoomId`), `server/server.js:376-389`.
- The token's `room` is the authorization boundary: a token for `design-team`
  cannot join `ops`, even if `ops` is allowlisted.
- Every signaling event re-checks authenticated session, emitter room, target room,
  and (for answers) a recorded directed offer: `server/webrtc.js:91`, `:150`, `:209`,
  `:234`, `:263`.

## 8. Recommended implementation order

1. **P4-1 — stabilize the frontend baseline** (test timeout/config; investigate 4 s
   mounts). Rationale: every later claim depends on trustworthy green runs; it is
   low-risk and does not change product behavior. Do not weaken assertions.
2. **P0-1/P0-2/P0-3 — physical audio, permission recovery, crossfade** (requires the
   hardware blocker to clear). These decide whether the product's core promise works.
3. **P0-4/P0-5 — real interruption matrix** (offline/online, heartbeat timeout,
   server restart, crash during negotiation). Highest remaining reliability risk.
4. **P1-1/P1-3/P1-4 — HTTPS guard, token-refresh E2E, remove bundled join code.**
   Cheap, high-value hardening; no new infrastructure.
5. **P1-2/P1-6 — identity decision and optional membership ACL.** Architectural;
   do not start a custom auth system without the threat model and an IdP decision.
6. **P2-1/P2-2/P2-3 — relay-only verification, credential refresh, ICE restart.**
   Requires the TURN server; keep STUN behavior unchanged when unconfigured.
7. **P3-1/P3-2/P3-4 — 2/4/8-participant media measurements and network impairment.**
   Decide on an SFU only from these results (P3-3).
8. **P4-2/P4-3/P4-4/P4-5/P4-6 — deployment, CI, PowerShell guide, housekeeping,
   evidence archive.** Finish with a go/no-go report.

Dependencies: step 1 can start immediately; steps 2, 6, 7 are blocked externally;
steps 4–5 and 8 can proceed in parallel with the hardware/infrastructure work.

## 9. Go/no-go recommendation

### **NO-GO for production or public exposure**

Reasons:

1. No evidence of audible microphone-to-speaker audio in either direction.
2. No real TURN relay test or independent-network test; restrictive NATs remain
   unsupported in practice.
3. No browser-media scalability evidence; the mesh is O(n²), and only server
   signaling has been measured. A “50-user” claim is unsupported.
4. Identity is a signed application session, not a verified person; production
   issuance is disabled without a join code or upstream IdP.
5. The frontend regression suite is not green at baseline (2/153 timeouts on 3/3
   runs), so release evidence is currently unreliable.
6. No deployment/rollback runbook, CI pipeline, or TLS/HSTS enforcement.

### Conditional pilot (trusted network, ≤ 4 participants)

Acceptable only after:

- P0-1 manual two-microphone checklist passes and is recorded;
- P0-2 permission-recovery check passes;
- P1-1 HTTPS production origin guard is in place (or the pilot is HTTPS-fronted);
- P1-3 token refresh is verified end-to-end;
- P4-1 suite stability is demonstrated (5 consecutive green runs);
- participants are on a trusted network, and the operator accepts no TURN/NAT
  guarantee.

Do **not** claim production readiness, enterprise authentication, real TURN
connectivity, or 50-user media support until the corresponding evidence exists.

## 10. Audit limitations

- The audit machine was under significant background load (Chromium/agent/OneDrive).
  Counts and exit codes are reliable; durations and load-test numbers are
  indicative and differ from Phase 3.10 in both directions.
- The deterministic reconnect test cuts the Socket.IO transport; it does not simulate
  an abrupt OS-level network partition or heartbeat timeout.
- The fake media device produces digital silence; `track.muted` is not a reliable
  audibility signal, and packet counters are the media evidence used.
- No source files were modified. The build regenerated `dist/` with the same asset
  hash (`index-BmWbNTDa.js`). `server/tmp-prod.log` (53 bytes, one startup line) is a
  leftover artifact from earlier verification and is listed for cleanup in P4-5; it
  was not removed during this audit.
